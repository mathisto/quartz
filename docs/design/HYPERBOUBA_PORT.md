## 1. What hyper bouba is

`h` ("hyper bouba") is a small imperative scripting DSL by eli_oat. Not a graphics library — a *language*.

- **Scripts are strings.** State is **one flat, insertion-ordered key-value store**, dot-path addressed (`player.hp`). Every command reads from and writes to that store. English-like, data-last word order; connecting words (`to`, `into`, `from`, `by`, `onto`) are positional sugar.
- **~70 builtin commands**: arithmetic, collections, string/math utilities, aggregation, queries, iteration (`map`/`each`/`scan`), control flow (`when`/`unless`/`cond`/`assert`), and user functions (`on …do…end`) with `ref` write-back params, `local` temps, `?`-suffixed predicates, namespacing, and recursion capped at depth 64.
- **Three upstream implementations**, behavior-matched: `js/` (interpreter on `b.js`), `c/` (C89 port, arena allocator, single-header embeddable API), `c/hyperdrive/` (a game runtime *built as a host on top of the C core*).

The Quartz port targets the **C implementation** as its reference — it is the most complete, has the cleanest embedding seam, and `hyperdrive` is built on it.

### 1.1 The C core, structurally (`c/h.c`, ~2930 lines)

| Piece | C shape | Notes |
|---|---|---|
| Dynamic value | `HVal` tagged union: nil / bool / num(double) / str / array / obj / func | Recursive — arrays and objects nest `HVal`s. |
| State store | `HObj` — **growable flat array** of `{key, val}` entries | Insertion order is observable (`keys`/`values`/`each as key`). **Not a hash map.** |
| Memory | `b.h` arena: 32 MB persistent + 2 MB scratch, scratch reset per `h_run` | `b.h` = "BABA YAGA"-licensed single-header arena + SIMD primitives. |
| Pipeline | tokenizer → `h_parse` (AST of `HNode`) → `h_eval_node` / `h_eval_ast` / `h_eval_cond` | One statement per `HNode`; `;`/`then`/newline are separators. |
| Dispatch | name → `cmd_*` function table | ~70 builtins, each a `cmd_*`. |
| **Host seam** | `h_register(name, fn)` + `on_set` mutation observer hook | **This is the extension API.** Hosts add commands and observe state writes through it. |

### 1.2 hyperdrive, the reference host (`c/hyperdrive/`)

A game runtime: a `.hb` script, a 160×100-pixel window, a 16-color palette, keyboard+mouse, a 60fps `on init / on update / on draw` loop. It adds — purely via `h_register` — the command families `screen.* key.* sfx.* synth.* sound.* image.* tilemap.* tween.* signal/connect/emit collision.* state.*`. Backed by **TIGR** (a tiny OpenGL-windowed framebuffer library) and **miniaudio** + cmixer for sound. It ships `--check`, `--lint`, `--trace`, `--dev` (live reload), `--fps`.

The decisive observation: hyperdrive's *drawing* (`screen.rect`, sprites, `tilemap.draw`, text) and its *synth/sfx* are pure memory writes and DSP math. TIGR only does `{create window, present a pixel buffer, poll input}`; miniaudio only does `{open device, pull PCM}`. The graphics/audio *device* surface is tiny and irreducible; everything above it is portable logic.

## 2. Architecture

Two layers, three hosts. The layering mirrors `h`'s own design — Quartz does not invent an abstraction, it inherits one.

```
┌─────────────────────────────────────────────────────────────┐
│ Layer 1 — Hosts (each adds commands via the register seam)   │
│                                                              │
│  Host A: hyperdrive   Host B: TUI         Host C: framebuffer│
│  (parity port)        (reuses std/tui/)   (SDL-backed)       │
│       │                    │                   │            │
│       └──── thin FFI ───────┴── std/tui/ ───────┴── thin FFI │
│            (TIGR+miniaudio)                       (SDL2)     │
├─────────────────────────────────────────────────────────────┤
│ Layer 0 — `h` core (100% Quartz-native)                      │
│  HVal · ordered KV store · tokenizer · parser · evaluator    │
│  ~70 builtin commands · user functions · register/on_set     │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 Layer 0 — the `h` core, in Quartz

A faithful port of `c/h.c`. Port the **semantics**, not the C allocator.

- **`HVal`** → a recursive Quartz enum with payloads (stable today, v5.25-alpha):
  ```
  enum HVal
    Nil
    Bool(b: Bool)
    Num(n: Float)
    Str(s: String)
    Arr(items: Vec<HVal>)
    Obj(store: HObj)
    Func(def: HFuncDef)
  end
  ```
- **`HObj`** → **a `Vec<HEntry>`, not a `Map`.** Fidelity-critical: hyper bouba's KV store is insertion-ordered and `keys`/`values`/`each … as key` expose that order. Quartz's `Map<K,V>` is hash-backed and does not guarantee iteration order. The port keeps an ordered vector; a hash index alongside it is a *later* optimization, only if profiling demands it. (Dogfood note: if this is painful, an ordered-map type is a legitimate `std/collections` gap to file.)
- **Memory** — use Quartz's `Arena` (`std/memory.qz`) for per-run scratch (tokens + AST), reset between `h_run` calls, matching `h`'s scratch discipline. Persistent state uses ordinary Quartz ownership. The 32 MB/2 MB constants are C arena sizing artifacts and do not port.
- **Pipeline** — tokenizer, recursive parser to an `HNode` AST, tree-walking evaluator. Command dispatch is a `Map<String, HCmdFn>` (the dispatch table is keyed at runtime by host registration, so a `match` cannot be used wholesale).
- **Host seam** — `hb_register(state, name, fn)` and an `on_set` observer callback must be preserved exactly. They are how all three hosts attach. `HCmdFn` is a Quartz function value `Fn(HState, args): Int`.

### 2.2 The thin FFI seam (decision: confirmed 2026-05-16)

For the hyperdrive parity host and the SDL host, Quartz owns the framebuffer and **all** rasterization and DSP. FFI is restricted to the irreducible device layer.

- **Graphics** — Quartz allocates an RGBA pixel buffer and implements every drawing op (`screen.clear/rect/line/pixel/text`, sprite blits, `tilemap.draw`, the bitmap font). FFI calls a ~6-function C shim over TIGR: `{open window, present buffer, closed?, poll keyboard, poll mouse, free}`.
- **Audio** — Quartz implements the synth and sfx DSP and renders PCM frames into a **shared ring buffer**. The miniaudio device callback (pure C, runs on miniaudio's own thread) *drains* the ring. This is a deliberate **push model**: it means **no C→Quartz upcall** and no FFI-thread re-entry into Quartz — the hard part of audio FFI is designed out.
- **Input** is polled by the Quartz-driven main loop each frame; also no upcall.
- **Build** — `quartz` → `.ll` → `llc` → `clang` links the program `.o` with the C shims and platform libs (`-framework OpenGL -framework Cocoa` on macOS; `-lGL -lX11` on Linux; `-lSDL2` for Host C). Wired as a `quake` task or a small project Makefile.

Net C surface for full hyperdrive parity: roughly two shim files, well under 200 lines of C. Everything else is Quartz.

### 2.3 Layer 1 — the three hosts

| Host | Order | Backend | Stance |
|---|---|---|---|
| **A — hyperdrive** | 1st | Quartz framebuffer + TIGR/miniaudio seam | **Perfect-fidelity port.** No creativity, no "improvements." eli's ergonomics preserved exactly. Part of the upstreamable artifact. |
| **B — TUI** | 2nd | Existing `std/tui/` | Creative. New command surface mapping `h` state → TUI cells. Co-design naming with eli. Quartz-repo-only. |
| **C — framebuffer/SDL** | 3rd | SDL2 via FFI; shares Host A's framebuffer + raster code | Modest: **same 160×100 / 16-color model** as Host A, just a larger desktop window. Effectively a backend swap (SDL for TIGR), not a new host. **Candidate for `std/gfx/` promotion** (§5). Quartz-repo-only. |

### 2.4 Dual home — Quartz demo *and* upstreamable fourth implementation

The port has two destinations; one source tree serves both.

- **In the Quartz repo** — `examples/hyperbouba/` is a flagship multi-file demo, peer to `examples/chip8/`, part of Quartz's project demo library. This is where it is built and where it lives now.
- **In eli's repo** — the *parity* subset (core interpreter + hyperdrive, HB.0–HB.3) is structured so its contents map 1:1 onto a `quartz/` directory in `~eli_oat/h`, beside `js/` and `c/`, as a **conformant fourth implementation** of the frozen spec.

## 3. Fidelity strategy — how "perfect port" is made *measurable*

The parity goal is only credible if it is testable. Three mechanisms, in increasing strength:

1. **Spec corpus.** Every code block in eli's `ref.md` and `learn.md` is a behavior assertion. Transcribe them into QSpec cases.
2. **Conformance suite.** Port eli's `js/tests/unit/verify-*.js` (~22 files — arithmetic, collections, control flow, string, iteration, functions, parser, tokenizer, …) to QSpec. This is the explicit behavior contract shared across all three upstream implementations; the Quartz port becomes a fourth conformant implementation.
3. **Differential state oracle (HB.0).** The C core has *no* `--trace` flag — that earlier draft of this section was inaccurate. The C reference's standalone runner is `c/hrun.c`: it reads a script from stdin and dumps the final state, as text or (`--json`) as a JSON object; `c/test_hrun_json.sh` is its conformance harness. The HB.0 oracle is therefore a **final-state diff**: for every non-hyperdrive `.h` script (every `ref.md` / `learn.md` example), run C-`hrun --json` and Quartz-`hrun --json` and diff byte-for-byte. The Quartz side is `examples/hyperbouba/hrun.qz` — a faithful port of `c/hrun.c`, same stdin interface and same two formats, so `test_hrun_json.sh` runs against it unchanged. The harness that drives this is `examples/hyperbouba/spec/oracle.sh` (HB.0, thirteenth slice — see §9): it extracts every fenced block from `ref.md`/`learn.md` at the pinned commit, feeds each to C-`hrun --json` and Quartz-`hrun --json`, and diffs byte-for-byte. It is a *C-vs-Quartz* differential — it does not check output against the docs' prose, since an example needing a preset starting state still agrees between the two runners (both lack the same setup); documented-behavior assertions are the conformance suite's job (mechanism 2). Any divergence is a fidelity bug with an exact reproducer. *(A stronger per-mutation trace exists only in the JS reference — `js/tools/h-trace.js` via `traceScript`; a per-statement trace is HB.1+ work since hyperdrive's `--trace` is where the C side gains one.)*
4. **Golden-frame game runs** (hyperdrive). With a seeded RNG and a scripted input sequence, a hyperdrive game is deterministic. Record per-frame framebuffer hashes from C hyperdrive; replay under Quartz hyperdrive; diff. `bubble-gum-hop` and `space-shmup` are the integration targets.

**Determinism prerequisite.** `roll` / `math.rand` mean the C PRNG must be reproduced *exactly* (same algorithm, same seeding) for (3) and (4) to hold. Likewise the number formatting (`5` vs `5.0`, float precision) must match byte-for-byte — the `hrun --json` oracle exercises this directly (a fractional value renders through `f64_to_str`). Both are tracked open items (§7).

## 4. Dogfooding plan (goal 1)

This port is a real-world Quartz workload chosen partly to stress the compiler. Expected pressure points, each a chance to find a hole:

- **Recursive enums with payloads at scale** — `HVal` is the v5.25-alpha union/record feature exercised hard and recursively.
- **Ordered KV store** — may surface a `std/collections` gap (ordered map).
- **Recursion + an explicit depth guard** — the 64-deep user-function limit.
- **String interpolation** — hyper bouba has its own `{key}` interpolation; implementing it tests Quartz string handling.
- **Closures as values** — `HCmdFn` host callbacks stored in a dispatch map.
- **FFI** — the device seam is a genuine multi-library link (`OpenGL`/`Cocoa`/`X11`/`SDL2`, miniaudio threads).
- **Pattern matching** — command dispatch and AST evaluation.

**Discipline (CLAUDE.md D1/D6):** when the port hits a compiler limitation, the default is to *fix the compiler*, not to contort the Quartz source. Holes that aren't fixed in-session are filed as `HB-DOG.n` roadmap rows. Silent workarounds are a directive violation.

## 5. Stdlib boundary (decision: confirmed 2026-05-16 — "earn it")

- The **`h` interpreter** is an application, not stdlib. It lives in `projects/hyperbouba/` permanently.
- The **TUI host** reuses the *existing* `std/tui/`. It adds no stdlib.
- The **windowing / framebuffer / input / audio-device layer** built in Phase 2 starts app-local. **If** it generalizes cleanly when the SDL host (Host C) consumes it, a separate roadmap item promotes a `std/gfx/` module. It is not designed as stdlib up front — generality is earned by a second consumer, not assumed.
- **Nothing goes into the language itself.** Dogfooding fixes compiler holes, but hyper bouba needs no new Quartz *syntax*.

### 7.1 Host ergonomics — decisions (HB.4/HB.5)

Working decisions made 2026-05-16, to be confirmed with eli (he's in the loop). Framing: this port is a gesture of love to a friend and a dogfooding vehicle — **fidelity and restraint over ambition.**

1. **Shared vocabulary.** Non-hyperdrive hosts reuse hyperdrive's exact command names (`screen.rect`, `screen.text`, `key.up`, …). A new idiom is coined *only* where a host genuinely cannot express a hyperdrive command. By default a `.hb` script ports across hosts unmodified.
2. **Documented host contract.** hyper bouba gets a written host-interface spec — the `on init/update/draw` hook set + the command-registration / `on_set` contract — so hyperdrive, TUI, and SDL are all instances of one documented pattern. Write this doc when HB.4 starts.
3. **Normalize to hyperdrive's model.** All hosts normalize down to 160×100 / 16-color / hyperdrive's input model. The constraints are deliberate — a fixed small canvas is part of the design's character, not a limit to escape. A `.hb` game runs everywhere unmodified.
4. **TUI input degradation accepted.** The terminal host provides `key.pressed.*` (edge) only; `key.*` (held) cannot be faithfully reproduced in a raw terminal and degrades to best-effort. Acceptable for the TUI host.
5. **SDL host — modest scope.** "hyperdrive with a bigger window": same 160×100/16-color model, same API, scaled to a larger desktop window. No true-color, no larger sprites, no expanded audio — only what's necessary. Revisit only if a concrete need appears.
6. **Naming review.** New command names / grammar are run past eli as proposed — the language keeps feeling like his.

**Consequence.** Decision 3 (normalize) + decision 5 (modest SDL) collapse Host C from "a new host" into "a second *backend* for Host A" — same framebuffer, same rasterization, same palette, SDL swapped in for TIGR. That shrinks HB.5 substantially and strengthens the §5 `std/gfx/` case: the device layer earns promotion by being proven identical across two backends.

## 8. Open questions / later decisions

- **PRNG parity — ✅ RESOLVED (eli's `be4a084`, 2026-05-16/17).** `roll`/`shuffle` used C's libc-dependent `rand()`, which would break the differential oracle (§3). Our C patch (xorshift32 + `h_seed()`) was **accepted verbatim** by eli, who then added a `seed` language command, matched the algorithm in `js/h.js`, and published cross-impl known-answer values (`js/tests/unit/verify-prng-parity-test.js`). The Quartz port (twelfth slice) ports the same xorshift32 into `HState.rng_state` plus `seed`/`roll`/`shuffle` — verified bit-for-bit against the published KAT: seed-1 stream `[270369, 67634689, 2647435461, …]`, `roll 100`→`70`, `shuffle [1..5]`→`[3,4,1,2,5]`. C, JS, and Quartz now agree byte-for-byte; `roll`/`shuffle` are no longer deferred. `math.rand` is not in the builtin set. **Spec pin advanced** to `be4a084` (origin/main) accordingly: that commit's `ref.md` carries the new `seed` command, its example block, and a Command-Index row — three commits past `d156192` (`8e14f85`, `f25e553`, `be4a084`). The differential oracle builds its C reference and reads its docs from `be4a084`. (The local clone's working tree may sit elsewhere — a local `perf/interp-optimizations` branch, etc. — so the oracle uses `git show`/`git worktree` against the pinned commit, never the checkout.)
- **`math.rand` is still on libc `rand()` — not cross-impl deterministic.** The PRNG-parity work above fixed the **`h` core** (`roll`/`shuffle`/`seed` → seeded xorshift32, KAT-verified). But the *hyperdrive* layer's `math.rand` / `math.rand.int` (`hd_cmds.c`) still call libc `rand()`, seeded `srand(time(NULL))` — so a script that *renders* off `math.rand` produces a different framebuffer on every C run and cannot be matched by the Quartz port. The HB.2 render oracle (§9 slice 7) classifies every `math.rand`-tainted script as an expected `xfail`. The fix is the same shape as the core PRNG fix: move `hd_cmds`' `math.rand` family onto the `h` core's seeded xorshift32 (exposed as a host-callable rng), upstream, jointly with eli. Until then, `math.rand` rendering is a documented C-vs-port divergence, not a port bug. The same `xfail` bucket also holds `debug.arena.used` / `debug.arena.cap`: they report the C interpreter's 32 MB bump-arena byte counters, an allocator the Quartz port's interpreter does not have — the port no-ops them by design (`hyperdrive.qz`), so any script rendering those counters diverges unconditionally.
- **Number formatting** — `h_val_to_str`'s integer-vs-float rendering and float precision must match C byte-for-byte. Resolve in HB.0.

- **Container stringification — C vs. spec/JS divergence.** C's `h_val_to_str` renders an array as the literal `"[array]"` and an object as `"[object]"`. The frozen spec (`ref.md`:148 — "Arrays are converted to `"a,b"` form") and the JS reference (`String([1,2,3])` → `"1,2,3"`) instead comma-join the elements. Our port's `hb_val_to_str` is faithful to **C** (`"[array]"` / `"[object]"`), consistent with §3's "C is the reference target." This surfaces anywhere a container is stringified: `str.len`, `str.concat`, `{key}` interpolation, `log`, the `has` operator, the `sort` / `group` key paths. It is the same shape as the `each`/`it` divergence — C disagreeing with its own spec and the JS reference — so by that precedent C's `"[array]"` is the bug, and the fix is a one-line `h_val_to_str` change upstream plus the matching `hb_val_to_str` change here. Deferred as a *decision*: unlike `each`/`it` (localized to one command), this ripples through every array-stringifying trace, so flipping it without also patching C would make the `--trace` differential oracle noisier. Resolve jointly with eli, alongside the number-formatting item.
- **Build integration** — `quake` task vs. project Makefile for the multi-library link. Resolve in HB.2.
- **`std/gfx/` promotion** — decided at HB.5, contingent on the device layer generalizing across Host A and Host C.
- **Trailing-dot remove micro-divergence** — `hb_remove_path("a.")` removes key `a`, whereas C's `h_remove_path` splits at the last dot and removes the empty leaf key from object `a` (a no-op). Only affects malformed trailing-dot paths, which no real script uses; the `--trace` differential will not exercise it. Filed for completeness; fix only if a real divergence surfaces.
- **Arithmetic on an explicitly-nil key** — `mul`/`div` default a *missing* destination to `1.0`. The dot-path lens (`hb_get_path`) returns `HNil` for both an absent key and a key holding a stored `nil`, so a stored-nil destination is treated as missing (→ default `1.0`), whereas C distinguishes them (`NULL` → default, present `H_NIL` → coerced to `0`). No command in the HB.0 slice so far produces a stored nil, so the divergence is unreachable today; revisit if a future command can store `nil`. The fix is an existence probe on the lens — that probe now exists (`hb_state_exists`, added for the predicate-restore path), so closing this divergence is a one-line change in `hb_apply_arith` if a stored-nil-producing command ever lands.
- **`h_call_user_fn`'s save arrays are dead code** — C's `h_call_user_fn` allocates `saved_params` / `param_existed` and populates them, but never reads them: cleanup unconditionally `h_remove_path`s every param/ref/local. So a user-function call that shadows an existing state key **drops** that key when it returns rather than restoring its prior value. The Quartz port reproduces the observable behavior (remove, never restore) and omits the dead arrays. If this ever proves to be an upstream bug rather than intended, the `--trace` differential will not catch it (both implementations behave identically) — it would need a direct cross-check with eli.

- **`each` cleans up `it` — ✅ RESOLVED upstream (`d156192`, 2026-05-16).** *Was:* C's `cmd_each` deliberately left `it` in the state store after the loop (an arena-leak-avoidance rationalisation), diverging from the frozen spec (`ref.md`:276) and the JS reference (both say `each` removes `it`) — C's own suite carried 5 `each`-cleanup assertions that all failed against its own `cmd_each`. The Quartz port followed the spec from the start (`hb_cmd_each` removes `it` on completion, restoring a pre-existing outer `it`). eli has now merged the C fix as `d156192` — `cmd_each` removes `it` and restores any outer `it`, using an if/else (not remove-then-set) to avoid the arena re-alloc that originally motivated the leak. C, JS, and the Quartz port now agree; the differential oracle no longer diverges on `each`. `map` / `scan` were always correct in C and port verbatim.

- **Container-identity equality is not reproducible.** C's `h_val_eq` falls back to pointer identity for arrays / objects (`a == b_`), so `filter pairs where it != <stored-tuple>` can drop the one tuple previously captured into a key — the "overworld" remove-matched-tuple pattern (`each` marks a tuple, `filter` removes it by `!=`). The Quartz `HVal` is a by-value enum with no stable pointer identity; `hb_val_eq` treats every container pair as unequal (a scalar-only contract, documented at its definition). The overworld each+filter test is therefore parked as `it_pending` in `eval_spec.qz`. No HB.0 command *produces* this pattern except that test; resolving it needs either a value-identity scheme (an interned id on container HVals) or a deep structural `==` for containers — decide if/when a real script or a later host needs it. **`unique` is the same root cause** — it dedupes via `hb_val_eq`, so an array whose elements are themselves arrays / objects is never deduped (C dedupes by pointer identity, which fresh allocations rarely share anyway). Scalar lists — the realistic and only-tested case — dedupe correctly. No HB.0 script unique-dedupes containers.

- **Host-API setters fire `on_set` only on key creation — faithfully reproduced (HB.3).** C's `h_setnum` / `h_setstr` / `h_setbool` — the host-side scalar setters the hyperdrive command layer writes results through (`collision.aabb`, `tilemap.get*`, `math.sin`/`cos`, the tween tick, `default`, `push_input`) — fire the `on_set` observer **only when the key is created**. When the key already exists they mutate the scalar slot in place and `return` without notifying the observer (`h.c`: `if (v) { v->u.n = val; return; }`) — C cannot supply a meaningful `old` once it has overwritten the slot. The DSL-level setters (`put` / `set` / `add` …) go through `h_set_path`, which always fires. The Quartz port reproduces this exactly: `hd_set_num` / `hd_set_bool` / `hd_set_str` (`hyperdrive/cmds.qz`) are creation-gated — `hb_state_set` (observer) on a new key, the raw `hb_set_path` lens (no observer) on an existing one. Observable only under `--trace` / `--trace-all` (the observer is a no-op otherwise), so gameplay is unaffected; surfaced by the HB.3 trace differential oracle, which would otherwise log one mutation per write where C logs one per key. Flagged for eli's awareness — it is a C-implementation constraint that became observable behaviour, like the `each`/`it` and `[array]` items above; no joint decision needed unless eli wants the observer to see in-place mutations.

- **`map` / `scan` / `filter` / `partition` / `find` restore the `it` binder clear-first; `each` and predicates restore if/else — faithfully reproduced (HB.3).** Two restore shapes coexist in `c/h.c`. `cmd_each` (post-`d156192`) and the predicate path do `if (saved) h_set_path(key, saved); else h_remove_path(key)` — an in-place change a `--trace` log shows as `it: old -> new`. `cmd_map` / `cmd_scan` / `cmd_filter` / `cmd_partition` / `cmd_find` do `h_remove_path(key); if (saved) h_set_path(key, saved)` — the restoring write always lands on an absent key, logged as a fresh `it = new`. The two produce an identical final store; they differ only in the trace form, and only when the loop is nested inside another `it`-binder (an outer `it` to restore). The port mirrors each command to its C counterpart: `hb_restore_key` (if/else) for `each` + predicates, `hb_restore_key_clear` (clear-first) for the other five (`core/eval.qz`). Surfaced by the HB.3 trace oracle on the nested `map`/`map` in `hyper-tracker`.

**HB.5 — DEFERRED (2026-05-18).** The SDL host as §7.1 decision 5 scoped it — an SDL2 backend swap of the TIGR window — is deferred indefinitely. **HB.4 follow-up — the first real-game runs (2026-05-18).** Hands-on runs of eli's games surfaced three things; two are explained, one is fixed.

*The windowed clock — root-caused to HB-DOG.14, FIXED.* On the TIGR host the per-frame `dt` was denormal garbage (`~6e-310`), so `time.dt` was effectively 0 and every `time.dt`-driven mechanic froze (caught via `collector.hb`'s countdown timer, which never decremented). A `time.dt` probe confirmed it — `dt` read as a denormal on the TIGR host, correct on the TUI host. Root cause: **HB-DOG.14** — an `extern "C"` function returning `F64` is miscompiled (the result is read from the integer register, not the C ABI's FP register), and the TIGR clock `hd_dev_time` → `tigrTime()` crossed the FFI boundary as an `F64`. This is also the cleaner design — one monotonic clock per backend — and it unifies the TIGR and TUI hosts. Verified: both hosts build + link clean, the driver and TUI specs are green, the headless path is unregressed (`bounce.hb` 15482 black px; the headless fixed-`dt` probe reaches `elapsed = 2.0` after 120 frames at 1/60). The windowed `dt` itself needs a display to confirm (the probe is the check). The underlying compiler bug HB-DOG.14 was subsequently fixed outright (2026-05-19 — see the HB-DOG.14 entry in §9); the Int-only seam is kept regardless as the cleaner one-clock-per-backend design.

*"space-shmup unresponsive to input" — explained, not a bug.* An initial "interpreter slowness" guess was measured and disproven (space-shmup runs ~600 fps headless; `title_update` runs every frame; forcing the keypress headlessly starts the game cleanly — `cond`/`else`, `game.start`, the `when key.pressed.space` chain all verified). What looked like dead input was two mundane things: on the TIGR host, the window opens **unfocused** — a terminal-launched, non-bundled macOS GUI binary does not get key focus until the user clicks it (~8–10 s in practice); eli's own C `hyperdrive` behaves identically, so it is not a port bug (an optional improvement: have the C shim call the Cocoa activation API on open). On the TUI host it is Finding A below, amplified — space-shmup's full-screen scrolling starfield changes nearly every cell every frame.

*`collector.hb` plays in the TUI host but is slightly laggy — OPEN.* The lag is suspected (not yet measured) to be the **TUI present path** — `term_build_plane` rebuilds 8000 `Cell`s + 16000 `Channel`s per frame and `renderer_diff` emits truecolour SGR for every changed cell; a full-screen-churn game defeats the diff renderer. Candidate levers (none a slam dunk — a terminal is not a fast framebuffer): cut `term_build_plane` allocation churn; emit 256-colour SGR instead of 24-bit truecolour for shorter escapes (`std/tui/render` emits truecolour only by design today); adaptive frame-skip. Not a release blocker — the TUI host is a creative extra.

- **HB-DOG.5 — ✅ FIXED 2026-05-17 — compiler segfault: a generic AST walker recursed into a non-node `extra` slot.** `quartz` itself crashed (exit 139, "index out of bounds: index \<huge pointer\>, size \<N\>") compiling the pattern below. Self-contained 18-line repro:
  ```
  enum Tree
    Leaf(v: Int)
    Branch(kids: Vec<Tree>)
  end
  def main(): Int
    t = Tree::Branch(vec_new<Tree>())
    match t
      Branch(kids) => {
        var k = 0
        while k < kids.size
          match kids[k]              # <-- inner match on a Vec<recursive-enum> element
            Leaf(v) => print_int(v)
            _ => print("br\n")
          end
          k += 1
        end
      }
      Leaf(v) => print_int(v)
    end
    return 0
  end
  ```
  **Root cause (diagnosed via lldb on the staged compiler).** The crash was in `typecheck_expr_handlers.qz`'s `tc_find_break_value_type` — a helper that scans a loop body for `break <value>` to type a loop-as-value expression. It is a *generic* AST walker: it recurses into `left` / `right` / `extra` / `children` of every node. But the `extra` slot is overloaded (`AstStorage.extras` is documented "Extra data — flags, metadata"). For `NODE_ENUM_ACCESS` (kind 39 — `Tree::Branch`, `Branch(kids)`), `extra` holds the `bound_names` **`Vec` handle** — a heap pointer, not a child node id. The walker recursed into that pointer (~`0x600000…`, a huge positive value) as if it were a node id; its only entry guard was `if node < 0`, which a huge *positive* pointer passes — so `ast_get_kind(storage, pointer)` indexed `kinds[pointer]` → OOB → bounds panic. (The bounds panic then `longjmp`'d to a stale/corrupt per-thread panic jmpbuf → `EXC_BAD_ACCESS` in `_longjmp` instead of a clean abort+backtrace — a *separate* latent bug, filed as HB-DOG.7.) The "recursion is the trigger" observation was a red herring: the crash needs only that the break-scan reach a `NODE_ENUM_ACCESS`; whether the enum is self-referential merely changes which typecheck path invokes the scan.
  **Fix.** `tc_find_break_value_type`'s entry guard now also rejects `node >= ast_node_count(ast_storage)`. Every recursive call re-enters through the guard, so any non-node value (a heap pointer, an out-of-range int) in any slot is safely ignored. The change is byte-identical for every program that previously compiled (the new bound is only reached by ids that previously crashed). `quake guard` PASSED — fixpoint verified (gen1 == gen2, 2532 fns); `style_demo` / `brainfuck` Bootstrap-Island Rule-2 smokes green; `quake qspec` clean (the 3 problem files — `float_f32_spec`, `random_effect_handlers_spec`, `wasm_data_spec` — fail/flake identically on the pre-fix golden, so they are pre-existing and unrelated). `crash5.qz` now compiles (exit 0). - **HB-DOG.7 — ✅ FIXED 2026-05-19 — internal panic in a no-scheduler program `longjmp`s to a garbage jmpbuf → `SIGSEGV`.** Found while diagnosing HB-DOG.5: when `qz_bounds_panic` / `qz_map_key_panic` / the `panic` intrinsic fire, they check `__qz_panic_jmpbuf_get()` and, if non-null, `longjmp` instead of abort-with-backtrace.   end

  end

It passed silently wherever `Int` coerced (`Fn(): Bool` / `Fn(): Int` accessors typechecked fine) and failed `QZ0200 "Return type mismatch: expected F64 but got Int"` where it did not. **Root cause** (the original "call typechecker ignores the binding" framing was one layer too shallow): the call *does* consult the binding's annotation string — but for an *inferred* local the annotation is reconstructed at bind time from the init expression's type via `tc_type_name_full`. `tc_type_name_full` had no case for Fn ptypes, so it rendered the `Fn(): F64` ptype with the generic `Function<arg1>` fallback → the binding's `type_ann` became the garbage string `"Function<Int>"`, and the call site's `tc_fn_annotation_return_type` (which scans for `"): "`) found no return type and defaulted to `Int`. **Fix.** `tc_type_name_full` (`typecheck.qz`) now renders a `TYPE_FUNCTION` ptype as its real registered annotation — the fn-type registry already stores the original `Fn(...): R` string (`tc_fn_type_annotation`). This also corrects `QZ0200`/diagnostic output, which previously printed function types as `Function<…>`. `quake guard` PASSED (fixpoint gen1==gen2, 2539 fns); `style_demo` / `brainfuck` Rule-2 smokes green; regression in `spec/qspec/fn_as_struct_field_init_spec.qz` (an inferred local from a non-Int Fn field, called). Fix-specific golden at `self-hosted/bin/backups/quartz-pre-hbdog13-golden`.

- **HB-DOG.14 — ✅ FIXED 2026-05-19 — an `extern "C"` function returning `F64` was miscompiled; the result was garbage.** Found 2026-05-18 in the HB.4 TUI-host debugging session: the windowed game clock (`hd_dev_time` → TIGR's `tigrTime()`, declared `extern "C" def hd_dev_time(): F64`) returned denormal garbage (`~6e-310`) instead of a frame delta, so `time.dt` was effectively 0 and every `time.dt`-driven mechanic (e.g. `collector.hb`'s countdown timer) froze. The C ABI returns a `double` in an FP register (xmm0 on x86-64); the Quartz call site read the result from the integer return register — so the bits were unrelated garbage. **Minimal repro** (link a Quartz `main` against a C file): C side — `double my_f64(void) { return 0.015625; }` and `long my_int(void) { return 42; }`; Quartz side — `extern "C" def my_f64(): F64` / `extern "C" def my_int(): Int`, then `my_f64()` printed `0` (a direct call) or `5.2e-310` (through a function-typed local — a denormal), while `my_int()` correctly printed `42` both ways. **Root cause** (two adjacent codegen gaps): (1) `cg_be_type_to_llvm` (`backend/codegen.qz`) mapped `CFloat`/`CDouble` to `float`/`double` but not the Quartz float types `F64`/`F32`/`Float`, so an `F64`-returning extern fell through to the `i64` default — the call was typed `i64` and read `rax`; (2) even when the LLVM return type *was* `double` (a `CDouble` extern), the extern-call codegen (`backend/codegen_instr.qz`) never reconciled the FP-register result with Quartz's uniform i64 slot — it emitted `store i64 %v, …` against a `double` SSA value, which `llc` rejected outright. **Fix:** `cg_be_type_to_llvm` now maps `F64`/`Float` → `double`, `F32` → `float`; the extern-call path emits the call into a `.fp` temp typed `double`/`float`, then bitcasts the result into the uniform i64 slot (`float` is `fpext`'d to `double` first, matching Quartz's double-bits-in-i64 slot representation of an `F32`). Symmetrically, declared `double`/`float` *parameters* now bitcast the i64 slot into a float at the call site (`float` additionally `fptrunc`s). `quake guard` PASSED (fixpoint, 2538 functions); regression coverage in `spec/qspec/ffi_spec.qz` ("FFI Float ABI (HB-DOG.14)" — IR-shape + runtime checks against libc `sqrt`/`pow`/`sqrtf`). The hyperbouba device seam keeps its Int-only design (`hd_driver_run_windowed` derives `dt` from `hd_device_mono_ns`) — that is the cleaner one-clock-per-backend design and is not reverted; the compiler fix simply removes the constraint.
